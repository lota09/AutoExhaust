## 📝 디버깅 기록: ESP8266 (Wemos D1 R1) 기술적 난제 해결

### 🔴 문제 1: 최신 라우터 WiFi 연결 실패 및 리셋
#### 1️⃣ 어떤 문제가 있었나
- TUF-AX5400 등 최신 공유기 환경에서 ESP8266이 WiFi 연결 중 멈추거나 `rst cause:4`(워치독 리셋) 발생.
- Smart Connect(2.4/5GHz 통합) SSID 환경에서 대역 할당 및 핸드셰이크 오류 발생.

#### 2️⃣ 어떤 시도를 해보았는가
- 기본 WiFi 예제로 연결 시도 -> 실패.
- 공유기 설정 변경 고려 -> 사용자가 선호하지 않음.

#### 3️⃣ 어느 순간 깨달았는가
- ESP8266의 기본 절전 모드와 통신 규격(802.11n/ax 대응 부족)이 최신 라우터와 충돌하고 있음을 인지.

#### 4️⃣ 어떻게 해결했는가
- **해결책**:
  - `WiFi.setPhyMode(WIFI_PHY_MODE_11G)`: 강제로 802.11g 모드로 설정하여 호환성 확보.
  - `WiFi.setSleepMode(WIFI_NONE_SLEEP)`: 절전 모드를 꺼서 패킷 유실 차단.
  - **결과**: ✅ WiFi 연결 및 유지 안정성 획기적 개선.

### 🔴 문제 2: 뱀부랩 MQTT 수신 시 중단 (Last state: -3)
#### 1️⃣ 어떤 문제가 있었나
- MQTT 연결은 성공(`Success.`)하지만, 데이터가 들어오는 순간 즉시 끊어지고 재접속 무한 반복.
- 로그에 `Disconnected! Last state: -3` (Connection Lost) 기록됨.

#### 2️⃣ 어떤 시도를 해보았는가
- SSL 버퍼를 512, 2048 등으로 조금씩 늘려봄 -> 여전히 실패.

#### 3️⃣ 어느 순간 깨달았는가
- 뱀부랩 프린터가 보내는 전체 상태 보고서(Full Report)가 **12.2KB**라는 거대 사이즈임을 확인. 
- SSL 프래그먼트가 표준 최대치인 16KB에 도달할 수 있음을 인지.

#### 4️⃣ 어떻게 해결했는가
- **해결책**:
  - `askClient.setBufferSizes(14336, 512)`: SSL 수신 버퍼를 14KB로 확장.
  - `client.setBufferSize(14336)`: MQTT 수신 버퍼 역시 14KB로 확장.
  - **결과**: ✅ 12KB 이상의 거대 패킷 수신 성공.

### 🔴 문제 3: 스택 오버플로우로 인한 갑작스러운 리셋 (Exception 3)
#### 1️⃣ 어떤 문제가 있었나
- 버퍼 확장 후 데이터 수신은 되나, 데이터를 읽는 순간 `Exception (3)` (LoadStoreError) 발생하며 리셋.
- `JSON Filtered Parse Error: NoMemory` 로그 동반 발생.

#### 2️⃣ 어떤 시도를 해보았는가
- `StaticJsonDocument` 크기를 줄여봄 -> `NoMemory` 에러가 더 심해짐.

#### 3️⃣ 어느 순간 깨달았는가
- ESP8266의 **스택(Stack) 메모리**는 4KB로 매우 제한적임.
- 1KB 이상의 JSON 도큐먼트를 스택에 선언하자 SSL/MQTT 라이브러리가 쓰고 남은 공간을 침범당함.

#### 4️⃣ 어떻게 해결했는가
- **해결책**:
  - `DynamicJsonDocument doc(1024)`: 스택 대신 여유로운 **힙(Heap)** 메모리를 사용하도록 변경.
  - **결과**: ✅ 스택 충돌 해결 및 파싱 안정화.

---

### 🔴 문제 4: 힙 고갈로 인한 시스템 폭주 (Exception 0)
#### 1️⃣ 어떤 문제가 있었나
- 한동안 잘 돌아가다가 어느 시점부터 `Exception (0)` (Illegal Instruction) 발생하며 리셋.
- 아무런 에러 로그 없이 즉시 사망하는 현상 발생.

#### 2️⃣ 어떤 시도를 해보았는가
- 이전에는 안정적이었던 16KB 버퍼 유지 시도.

#### 3️⃣ 어느 순간 깨달았는가
- 16KB 버퍼 2개(SSL, MQTT)를 동시에 잡으면 32KB를 점유함. 
- 시스템 예약 램을 제외하면 연속된 빈 공간(Heap)이 전혀 남지 않아 파편화(Fragmentation)에 매우 취약해짐.

#### 4️⃣ 어떻게 해결했는가
- **해결책**:
  - 버퍼를 **14KB(14336)**로 2KB씩 다이어트. 
  - 총 **4KB**의 여유 램 공간을 확보하여 시스템이 Background WiFi 작업을 안정적으로 수행할 공간 마련.
  - **결과**: ✅ 장시간 가동에도 Exception 0 발생하지 않음.

### 🔴 문제 5: PWM 밝기 제어 고정 문제 (Range Mismatch)
#### 1️⃣ 어떤 문제가 있었나
- PWM 값을 255 이상(255~1023)으로 줘도 밝기와 전류가 100%로 고정되는 현상.
- 5,000Hz 고주파 사용 시 MOSFET이 느려서 발생한 하드웨어 '쓰레기' 문제로 의심됨.

#### 2️⃣ 어떤 시도를 해보았는가
- 주파수를 20Hz까지 극단적으로 낮춰봄 -> 현상 동일(여전히 100%로 보임).

#### 3️⃣ 어느 순간 깨달았는가
- 측정값 분석: 예상 범위(1023)가 아닌 **255가 시스템 기본 최대치**임을 계산을 통해 도출. 
- 1023 기준 10%라고 생각한 값(102)이 실제로는 255 기준 40%로 작용하여 전류값이 비례하게 측정됨.

#### 4️⃣ 어떻게 해결했는가
- **해결책**:
  - `analogWriteRange(255)`: PWM 범위를 명시적으로 255로 고정하여 코드 상의 의도와 하드웨어 동작을 일치시킴.
  - **결과**: ✅ 1kHz 이상의 고주파에서도 정밀한 0~100% 밝기 제어 성공. (5kHz도 가능 확인)

---

## 🎯 핵심 교훈
- **8비트 MCU의 한계**: ESP8266은 램이 부족하므로 "연속된 메모리 할당"이 가장 큰 적이다. 1KB의 차이가 생사를 가른다.
- **스택 vs 힙**: 큰 구조체(JSON 등)는 반드시 힙을 써야 스택 오버플로우를 피할 수 있다.
- **추론의 중요성**: 오실로스코프가 없어도 전류 측정값과 소프트웨어 설정값의 비율 분석을 통해 하드웨어의 미스터리(PWM Range)를 풀어낼 수 있다.
